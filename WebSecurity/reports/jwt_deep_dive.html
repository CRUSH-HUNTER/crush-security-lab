§1

JWT چیست؟

What is a JWT

JSON Web Token یک فرمت استاندارد (RFC 7519) برای انتقال داده‌ی JSON، همراه با یک امضای رمزنگاری‌شده، بین دو سیستم است. معمولاً برای حمل «ادعاها» (claims) درباره‌ی هویت کاربر در فرایندهای احراز هویت، مدیریت سشن، و کنترل دسترسی استفاده می‌شود.

تفاوت کلیدی با سشن‌های کلاسیک

در مدل کلاسیک، سرور یک شناسه‌ی تصادفی کوچک به کلاینت می‌دهد و تمام اطلاعات کاربر را در دیتابیس خودش نگه می‌دارد. در JWT، برعکس است: تمام اطلاعات لازم داخل خود توکن ذخیره می‌شود و سرور فقط کافی‌ست امضا را تأیید کند — بدون نیاز به مراجعه به دیتابیس در هر درخواست. این ویژگی JWT را برای سیستم‌های توزیع‌شده با چند سرور بک‌اند محبوب کرده است.

نکته‌ی امنیتی بنیادین: چون همه‌ی داده داخل توکن و به‌صورت خوانا (Base64، نه رمزنگاری‌شده) قرار دارد، تنها چیزی که از دستکاری آن جلوگیری می‌کند «امضا» است. اگر بررسی امضا به هر شکلی ضعیف یا غایب باشد، کل مدل امنیتی فرو می‌ریزد.

§3

نحوه‌ی کارکرد در یک سیستم واقعی

Authentication Flow
  1. کاربر با یوزرنیم/پسورد لاگین می‌کند.
  2. سرور هویت را تأیید می‌کند و یک JWT امضاشده می‌سازد (شامل id، role و سایر claims کاربر).
  3. کلاینت این توکن را ذخیره می‌کند (در کوکی یا localStorage) و در هر درخواست بعدی، معمولاً در هدر Authorization: Bearer <token> می‌فرستد.
  4. سرور در هر درخواست، فقط امضا را تأیید می‌کند (نه یک جست‌وجوی دیتابیسی) و سپس به claims داخل payload اعتماد می‌کند.
نقطه‌ی حساس: مرحله‌ی چهارم دقیقاً همان‌جایی است که اکثر آسیب‌پذیری‌های JWT از آن سرچشمه می‌گیرند — اگر بررسی امضا ضعیف باشد، مهاجم می‌تواند claims (مثل role) را دستکاری کند و سرور بدون تشخیص، به آن اعتماد می‌کند.
§4

حملات شناخته‌شده روی JWT

Common Attack Classes
'none' Algorithm

استاندارد JWT اجازه می‌دهد الگوریتم امضا برابر none باشد (یعنی بدون امضا). اگر پیاده‌سازی سرور این حالت را قبول کند، می‌توان هر محتوایی را بدون نیاز به کلید، در payload گذاشت.

HMAC Key Confusion (alg confusion)

وقتی سرور از الگوریتم نامتقارن (RS256، با کلید عمومی/خصوصی) استفاده می‌کند، اما مهاجم الگوریتم را به HS256 (متقارن) تغییر می‌دهد و از همان کلید عمومی (که در دسترس همه است) به‌عنوان کلید امضا استفاده می‌کند. اگر سرور به‌اشتباه همان کلید را برای تأیید HS256 به کار ببرد، امضای جعلی پذیرفته می‌شود.

Embedded JWK Injection

برخی پیاده‌سازی‌ها اجازه می‌دهند خود کلید عمومی داخل هدر توکن (claim به نام jwk) جاسازی شود. اگر سرور منشأ این کلید را بررسی نکند، مهاجم می‌تواند کلید خودش را جاسازی و توکن را با آن امضا کند.

Weak Signing Key

اگر کلید مخفی HMAC ضعیف یا پیش‌فرض باشد (مثل secret یا changeme)، می‌توان با یک wordlist از کلیدهای رایج آن را Brute-force کرد.

kid Header Injection

هدر kid (Key ID) به سرور می‌گوید کدام کلید را برای تأیید امضا استفاده کند. اگر این مقدار بدون پاک‌سازی مستقیم در یک مسیر فایل یا کوئری دیتابیس استفاده شود، می‌تواند به Path Traversal یا SQL Injection منتهی شود.

jku / x5u Header Abuse

این هدرها به سرور می‌گویند کلید عمومی را از یک URL خارجی بگیرد. اگر سرور بدون بررسی به هر آدرسی وصل شود، مهاجم می‌تواند یک سرور کنترل‌شده معرفی کند (هم برای جعل کلید، هم برای شناسایی SSRF).

نمونه دستورات

# اسکن خودکار با jwt_tool
python3 jwt_tool.py <TOKEN> -M pb

# Brute-force کلید مخفی با jwt_tool
python3 jwt_tool.py <TOKEN> -C -d jwt.secrets.list

# Brute-force با hashcat
hashcat -a 0 -m 16500 jwt.txt jwt.secrets.list

تست‌های عملی انجام‌شده روی Juice Shop

Practical Testing Log
METHOD

استخراج و رمزگشایی Payload

با رمزگشایی دستی بخش Payload توکن واقعی، فیلد bid (Basket ID) شناسایی شد که مستقیماً به‌عنوان شناسه‌ی سبد خرید کاربر در API استفاده می‌شود — این یافته پایه‌ی تست IDOR در بخش دیگر گزارش شد.

{
  "data": { "id": 26, "role": "customer", ... },
  "bid": 7,
  "iat": 1787247421
}
MITIGATED

تست اعتبار امضا (روی change-password)

با حذف هدر Authorization و جداگانه با دستکاری امضای JWT، سرور در هر دو حالت با خطا پاسخ داد — اما از دو خط متفاوت در کد (بر اساس Stack Trace)، که نشان می‌دهد سرور هم وجود هدر و هم صحت امضا را به‌طور جداگانه بررسی می‌کند. این endpoint خاص در برابر دستکاری ساده‌ی JWT مقاوم است.

FOUND

تست الگوریتم 'none'

الگوریتم توکن به none تغییر یافت و امضا حذف شد؛ درخواست به یک endpoint محافظت‌شده ارسال شد.

نتیجه: سرور با کد 500 Internal Server Error پاسخ داد، همراه با یک Stack Trace کامل — یعنی به‌جای رد مودبانه‌ی توکن نامعتبر (401/403)، اپلیکیشن کرش کرد. این یک نمونه‌ی دیگر از آسیب‌پذیری Information Disclosure (مستندشده در گزارش اصلی) است، این‌بار از یک نقطه‌ی متفاوت در کد.
INCONCLUSIVE — NEEDS BASELINE

تست HMAC Key Confusion

الگوریتم از RS256 به HS256 تغییر یافت و توکن با یک مقدار جایگزین امضا شد. درخواست به GET /rest/continue-code ارسال شد و پاسخ 200 OK بدون محتوای معنادار دریافت شد.

چرا نتیجه هنوز قطعی نیست: این endpoint احتمالاً برای بازیابی سبد مهمان طراحی شده و ممکن است اساساً بدون نیاز به بررسی دقیق توکن، پاسخ 200 بدهد. برای تأیید واقعی حمله، لازم است:
۱. یک baseline با یک توکن کاملاً نامعتبر (garbage) روی همان endpoint گرفته شود.
۲. در صورت یکسان بودن نتیجه، حمله روی یک endpoint حساس‌تر (مثل basket API یا مسیرهای ادمین) با محتوای واقعی تکرار شود.
