یافته‌های تست امنیتی روی Juice Shop

مستندسازی تست‌های دستی انجام‌شده روی برنامه‌ی آسیب‌پذیر OWASP Juice Shop، از تحلیل CSRF تا افشای اطلاعات، IDOR و Clickjacking — با ابزار DevTools مرورگر (F12) و Burp Suite.

هدف: OWASP Juice Shop (Local) ابزار: DevTools / Burp Suite وضعیت کلی: ۵ تست کامل شد
Disclaimer: تمام تست‌های این مستند روی OWASP Juice Shop — یک اپلیکیشن عمداً آسیب‌پذیر و طراحی‌شده برای آموزش امنیت وب — و روی یک نمونه‌ی محلی (localhost) انجام شده‌اند. هیچ سیستم واقعی یا متعلق به شخص ثالث تست نشده است.
1

تست CSRF روی Change Password

Cross-Site Request Forgery — /rest/user/change-password
MITIGATED

مشاهده‌ی اولیه

درخواست تغییر رمز عبور به‌صورت GET ارسال می‌شود، با پارامترهای current, new, repeat در خود URL — این خودش یک ضعف طراحی است، چون متد GET طبق استاندارد HTTP باید «امن» (بدون تغییر وضعیت سرور) باشد.

GET /rest/user/change-password?current=X&new=Y&repeat=Y HTTP/1.1
Authorization: Bearer <REDACTED_JWT>
Cookie: token=<REDACTED_JWT>

تست ۱ — حذف کامل هدر Authorization

با حذف هدر Authorization (و باقی گذاشتن فقط کوکی)، سرور به‌جای پاسخ تمیز، با خطای مدیریت‌نشده پاسخ داد:

{
  "error": {
    "message": "Blocked illegal activity by ::ffff:172.17.0.1",
    "stack": "...at /juice-shop/build/routes/changePassword.js:61:18..."
  }
}

تست ۲ — دستکاری امضای JWT

با خراب کردن چند کاراکتر از بخش Signature توکن (نگه‌داشتن Header و Payload سالم)، دوباره همان خطا دریافت شد، اما این‌بار از خط متفاوتی در کد:

"stack": "...at /juice-shop/build/routes/changePassword.js:66:18..."
نتیجه: شماره‌خط متفاوت (۶۱ در برابر ۶۶) نشان می‌دهد سرور دو بررسی جدا دارد — یکی برای وجود هدر، دیگری برای اعتبار امضای JWT. یعنی این endpoint هم وجود هدر و هم صحت امضا را چک می‌کند؛ نمی‌توان با توکن جعلی یا کوکی به‌تنهایی آن را دور زد. مسیر مقاوم به CSRF کلاسیک است.

افشای اطلاعات از طریق مدیریت نادرست خطا

Information Disclosure via Improper Error Handling
FOUND

شرح

در طول تست CSRF، درخواست با هدر احراز هویت نامعتبر باعث بازگشت یک Stack Trace کامل به کلاینت شد — نه یک پیام خطای عمومی. این به‌خودی‌خود در Juice Shop به‌عنوان چالش رسمی Error Handling شناخته می‌شود.

اطلاعات افشاشده

از روی Stack Trace، این نکات درباره‌ی معماری داخلی سرور قابل استخراج بود:

- مسیر واقعی فایل‌ها روی دیسک سرور:
  /juice-shop/build/routes/changePassword.js
  /juice-shop/build/lib/utils.js
  /juice-shop/build/lib/insecurity.js
  /juice-shop/build/routes/verify.js

- فریم‌ورک بک‌اند: Express.js (Node.js)
- کد از TypeScript کامپایل شده (پوشه‌ی build)
- ساختار میان‌افزار (middleware chain) اپلیکیشن
اهمیت: در یک هدف واقعی (نه محیط تمرینی)، این نوع افشا به مهاجم کمک می‌کند حملات بعدی (مثل Path Traversal یا شناسایی نسخه‌ی آسیب‌پذیر کتابخانه‌ها) را دقیق‌تر هدف‌گیری کند.

روش‌شناسی: استخراج اطلاعات از JWT

Methodology — Decoding JWT Payload
METHOD

ساختار توکن

یک JWT از سه بخش جدا با نقطه تشکیل شده که هرکدام Base64URL-encoded هستند:

HEADER.PAYLOAD.SIGNATURE

بخش‌های Header و Payload بدون نیاز به کلید مخفی سرور، توسط هرکسی قابل رمزگشایی است — فقط Signature نیاز به کلید دارد.

روش‌های استخراج

# روش دستی (ترمینال)
echo "PAYLOAD_BASE64URL" | tr '_-' '/+' | base64 -d

# روش گرافیکی
https://jwt.io   (فقط برای توکن‌های تمرینی، هرگز روی سیستم واقعی)

# روش امن‌تر برای کار حرفه‌ای
Burp Suite → Inspector panel (رمزگشایی خودکار و محلی)

یافته‌ی کلیدی از Payload

در Payload توکن، فیلد bid (Basket ID) شناسایی شد که مستقیماً به‌عنوان شناسه‌ی سبد خرید کاربر در API استفاده می‌شود — نقطه‌ی شروع برای تست IDOR در Finding بعدی.

{
  "data": { "id": 26, "email": "...", "role": "customer", ... },
  "bid": 7,
  "iat": 1787247421
}

ابزارهای تخصصی برای ارزیابی امنیت JWT

ابزارکاربرد
jwt.ioدیکود سریع آنلاین (فقط برای توکن‌های تمرینی)
jwt_tool (ticarpi)اسکن خودکار آسیب‌پذیری‌های شناخته‌شده، جعل و دستکاری توکن
hashcatBrute-force کلید مخفی HMAC با wordlist
jwt-hackتست حمله‌های alg confusion، kid injection، claim tampering

تست IDOR روی Basket API

Insecure Direct Object Reference — /rest/basket/:id
CONFIRMED

فرضیه

اگر سرور هنگام دریافت درخواست GET /rest/basket/:id بررسی نکند که سبد خرید درخواستی واقعاً متعلق به کاربر لاگین‌شده است یا نه، می‌توان با تغییر عدد شناسه، محتوای سبد خرید کاربران دیگر را مشاهده کرد.

مراحل تست

۱. شناسایی basket ID خود کاربر از فیلد bid در JWT (اینجا: 7)
۲. درخواست مرجع:      GET /rest/basket/7
۳. درخواست‌های آزمایشی: GET /rest/basket/1
                       GET /rest/basket/2
                       GET /rest/basket/3 ...
نتیجه: درخواست با شناسه‌ی متعلق به یک basket غیر از شماره‌ی خودم، پاسخ 200 OK همراه با محتوای واقعی سبد خرید آن کاربر بازگرداند — بدون هیچ بررسی مالکیت روی سرور. یعنی سرور فقط چک کرده «آیا لاگین کردی؟» (Authentication)، نه «آیا این منبع خاص مال خودته؟» (Authorization). IDOR تایید شد.

تست Clickjacking

Clickjacking — Framing Protection Check
NOT VULNERABLE

فرضیه

بررسی این‌که آیا می‌توان صفحه‌ی Juice Shop را در یک iframe نامرئی روی یک دامنه/origin دیگر جاسازی کرد، به‌گونه‌ای که کاربر ناخواسته روی عناصر واقعی برنامه کلیک کند.

مراحل تست

۱. بررسی هدرهای پاسخ HTTP صفحه‌ی اصلی → یافت شد:
   X-Frame-Options: SAMEORIGIN

۲. ساخت یک صفحه‌ی HTML آزمایشی حاوی:
   <iframe src="http://localhost:3000"></iframe>

۳. سرو کردن این صفحه از یک پورت متفاوت (origin متفاوت از دید مرورگر):
   python3 -m http.server 9000
چالش جانبی: اجرای اولیه با پورت ۸۰۰۰ به خطای Address already in use برخورد کرد (پورت از قبل اشغال بود)؛ با تعویض به پورت ۹۰۰۰ رفع شد.

نتیجه

مرورگر بارگذاری iframe را کاملاً مسدود کرد؛ محتوای Juice Shop نمایش داده نشد و در Console خطای زیر ثبت شد:

Refused to display 'http://localhost:3000/' in a frame because it
set 'X-Frame-Options' to 'SAMEORIGIN'.
نتیجه‌گیری: از آنجا که صفحه‌ی آزمایشی و Juice Shop از دو origin متفاوت (پورت ۹۰۰۰ در برابر ۳۰۰۰) بودند، هدر X-Frame-Options: SAMEORIGIN طبق انتظار framing را مسدود کرد. برنامه در برابر Clickjacking کلاسیک محافظت‌شده است.

تست Directory Traversal روی /ftp/

Path Traversal — /ftp/:filename
MITIGATED

انگیزه‌ی تست

در Finding شماره ۲ (افشای اطلاعات)، مسیرهای واقعی فایل‌ها روی دیسک سرور از طریق Stack Trace افشا شده بود. این یافته به‌عنوان سرنخ برای بررسی این‌که آیا می‌توان از طریق endpoint دانلود فایل عمومی (/ftp/) به فایل‌های خارج از پوشه‌ی مجاز دسترسی یافت، استفاده شد.

مراحل تست

۱. تأیید عملکرد مسیر عمومی:
   GET /ftp/legal.md  →  200 OK (فایل متنی عادی بازگردانده شد)

۲. تلاش با ../ خام:
   GET /ftp/../package.json
   نتیجه: ریدایرکت به صفحه‌ی اصلی — مرورگر خودش مسیر را پیش از
   ارسال normalize کرد و درخواست اصلاً به سرور نرسید.

۳. تلاش با انکود URL:
   GET /ftp/..%2fpackage.json
   نتیجه: 403 Forbidden — این‌بار درخواست به سرور رسید و
   سرور آن را تشخیص داده و مسدود کرد.

۴. تلاش با ترکیب بک‌اسلش:
   GET /ftp/..\/package.json
   نتیجه: دوباره ریدایرکت (normalize شده توسط مرورگر)

۵. تلاش با دابل‌انکود و پیمایش تکراری:
   ..%252f  ,  ....//  ,  %2e%2e%2f
   نتیجه: همگی 403 Forbidden

نتیجه

Payloadنتیجهتفسیر
../RedirectNormalize شده توسط مرورگر، نرسیده به سرور
..%2f403رسیده به سرور، مسدود شده
..\/RedirectNormalize شده توسط مرورگر
..%252f403دابل‌انکود هم مسدود شد
....//403پیمایش تکراری هم مسدود شد
نتیجه‌گیری: Endpoint مورد آزمایش (/ftp/) در برابر تمام حالت‌های رایج دور زدن Directory Traversal — شامل انکود ساده، دابل‌انکود و ترکیب جداکننده‌های مسیر — مقاوم بود.

بای‌پس کامل احراز هویت از طریق JWT Algorithm None

Authentication Bypass — JWT 'none' Algorithm · CRITICAL
CRITICAL

خلاصه‌ی فنی

با تغییر الگوریتم امضا در هدر JWT از RS256 به none و حذف کامل بخش Signature، سرور چندین endpoint حساس را بدون هیچ اعتراضی قبول کرد. این یعنی این endpointها اصلاً صحت امضای توکن را بررسی نمی‌کنند — و مهاجم می‌تواند هر هویتی (از جمله admin) را بدون نیاز به اطلاعات لاگین جعل کند.

ساختار توکن جعلی استفاده‌شده

Header (decoded):
{
  "typ": "JWT",
  "alg": "none"      ← الگوریتم به none تغییر یافت
}

Payload (decoded):
{
  "data": {
    "id": 1,
    "email": "admin@juice-sh.op",
    "role": "admin"   ← نقش admin جعل شد
  },
  "bid": 1,
  "iat": 1787731669
}

Signature:           ← کاملاً حذف شد (رشته‌ی خالی)
روش ساخت توکن: در Burp Suite Repeater، تب JSON Web Token → تغییر alg از RS256 به none در بخش Header → تغییر payload دلخواه → حذف محتوای Signature → ارسال درخواست.

چرا بعضی endpointها بای‌پس شدند ولی بعضی نه؟

این الگو نشان می‌دهد که لایه‌ی میان‌افزار احراز هویت (auth middleware) در اپلیکیشن به‌صورت ناهمسان اعمال شده — بعضی مسیرها چک دقیق امضا دارند (change-password، whoami)، در حالی که بعضی دیگر اصلاً صحت امضا را بررسی نمی‌کنند (basket، Users، admin/application-configuration). این یک خطای طراحی سیستمی است، نه یک باگ منفرد و ایزوله.

ریشه‌ی اصلی آسیب‌پذیری: عدم اعمال یکسان و متمرکز بررسی امضای JWT روی تمام endpointهای محافظت‌شده. راه‌حل: یک middleware متمرکز که روی تمام مسیرهای نیازمند احراز هویت اعمال شود و الگوریتم none را صریحاً رد کند.
