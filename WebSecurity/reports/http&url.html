مرجع کامل URL و HTTP

خلاصه‌ی عملی از ساختار URL، پروتکل‌ها، متدهای درخواست و کدهای وضعیت پاسخ — همراه با مثال‌های واقعی، برای تمرین روی OWASP Juice Shop.

§1

URL Syntax

http://user:pass@www.joes-hardware.com:80/hammers;sale=false?item=12731#drills
بخشتوضیح
schemeپروتکل مورد استفاده — http, ftp, mailto و...
user:passwordاطلاعات ورود، مثلاً برای FTP
hostدامنه یا آی‌پی سروری که منبع رویش است
portپورت شنیداری سرور — پیش‌فرض HTTP برابر ۸۰ است
pathمحل منبع روی سرور، شبیه مسیر فایل‌سیستم
paramsپارامترهای هر بخش از مسیر، جدا با «;»
queryپارامترهایی برای اپلیکیشن‌های gateway، بعد از «?»
fragاشاره به بخشی داخل منبع؛ هرگز به سرور فرستاده نمی‌شود
Escape Encoding

چون URLها باید از پروتکل‌های مختلف به‌سلامت عبور کنند و برای انسان هم خوانا باشند، کاراکترهای ناامن با علامت درصد کدگذاری می‌شوند — مثلاً فاصله می‌شود %20 و خود علامت درصد می‌شود %25. کاراکترهایی مثل / ? # ; : هم چون معنای خاصی دارند، رزرو شده‌اند.

§2

Relative & Absolute URLs

Base URL

URL نسبی به‌تنهایی ناقص است؛ برای کامل‌شدن باید نسبت به یک base URL تفسیر شود. مثلاً اگر در صفحه‌ی tools.html یک لینک به ./hammers.html باشد، مرورگر scheme و host را از همان صفحه قرض می‌گیرد.

1. Path: ./hammers.html | Base: http://www.joes-hardware.com/tools.html 2. scheme خالی است → از base به ارث می‌رود: http 3. host/port خالی است → از base به ارث می‌رود: www.joes-hardware.com 4. ترکیب نهایی → http://www.joes-hardware.com/hammers.html
§3

A Sea of Schemes

http / https

پروتکل استاندارد وب. https همان http است با رمزنگاری SSL و پورت پیش‌فرض ۴۴۳.

https://www.joes-hardware.com/secure.html
mailto

اشاره به آدرس ایمیل، نه یک منبع قابل‌دسترسی مستقیم.

mailto:joe@joes-hardware.com
ftp

آپلود، دانلود و مشاهده‌ی فهرست فایل‌ها روی یک سرور FTP.

ftp://anonymous:pass@prep.ai.mit.edu:21/pub/gnu/
file

فایل‌های محلی روی یک دستگاه یا فایل‌سیستم شبکه.

file://OFFICE-FS/policies/casual-fridays.doc
news

دسترسی به گروه‌های خبری Usenet؛ به‌تنهایی کافی نیست، برنامه باید سرور NNTP را از قبل بداند.

news:rec.arts.startrek
telnet

دسترسی تعاملی و از راه دور به یک سیستم.

telnet://slurp:webhound@joes-hardware.com:23/
§4

HTTP Message Structure

CRLF

هر خط در پیام HTTP با دو کاراکتر تمام می‌شود: Carriage Return و Line Feed، که به‌اختصار CRLF نامیده می‌شود. برنامه‌های قدرتمند باید حالتی که فقط LF فرستاده می‌شود را هم بپذیرند.

Body

بدنه‌ی پیام، برخلاف خط شروع و هدرها، اختیاری است و می‌تواند متن، داده‌ی باینری یا خالی باشد. هدر Content-Type نوع بدنه را مشخص می‌کند و Content-Length اندازه‌ی آن را بر حسب بایت.

§5

HTTP Methods

GET
safe

پرکاربردترین متد. فقط می‌گه «این منبع رو برام بفرست» — قرار نیست هیچ اتفاقی رو سرور بیفته. هر سروری که HTTP/1.1 رو ساپورت کنه، مجبوره این متد رو داشته باشه.

HEAD
safe

دقیقاً مثل GET، ولی سرور فقط هدرها رو برمی‌گردونه، بدون بدنه. برای چک کردن وجود یا تغییر یک منبع، بدون دانلود کامل آن.

PUT
unsafe

برعکس GET — می‌نویسه، نه می‌خونه. بدنه‌ی درخواست رو می‌گیره و یا سند جدیدی می‌سازه یا سند موجود رو جایگزین می‌کنه. معمولاً نیاز به احراز هویت دارد.

POST
unsafe

برای فرستادن داده به سرور، معمولاً از فرم‌های HTML. داده به یک برنامه‌ی سمت سرور فرستاده می‌شود تا پردازش شود.

TRACE

یک ابزار تشخیصی — سرور همان درخواستی را که دریافت کرده، عیناً در بدنه‌ی پاسخ برمی‌گرداند تا مشخص شود پروکسی‌ها یا فایروال‌ها چیزی را تغییر داده‌اند یا نه.

OPTIONS

از سرور می‌پرسد «چه متدهایی را پشتیبانی می‌کنی؟» — به‌صورت کلی یا برای یک منبع خاص.

DELETE
unsafe

درخواست حذف یک منبع. نکته: تضمینی نیست که حذف واقعاً انجام شود — طبق مشخصات HTTP، سرور می‌تواند بدون اطلاع، این درخواست را نادیده بگیرد.

§6

Status Codes — 1xx Informational

100
Continue

کلاینت قبل از فرستادن یک بدنه‌ی بزرگ، از سرور تأیید می‌گیرد که آماده‌ی دریافت است — با هدر Expect: 100-continue.

101
Switching Protocols

سرور می‌گوید در حال تغییر پروتکل است، طبق چیزی که کلاینت در هدر Upgrade خواسته — مثلاً ارتقا به WebSocket.

§7

Status Codes — 2xx Success

200
OK

درخواست موفق بود، بدنه‌ی پاسخ همان چیزی است که خواسته شده.

201
Created

یک منبع جدید روی سرور ساخته شد. سرور باید پیش از ارسال این کد، واقعاً آن را ساخته باشد.

202
Accepted

درخواست پذیرفته شد، اما هنوز پردازش نشده — و تضمینی هم برای تکمیل آن وجود ندارد.

203
Non-Authoritative Information

اطلاعات هدرها از یک کپی واسطه آمده، نه مستقیم از سرور اصلی.

204
No Content

پاسخ هدر دارد ولی بدنه ندارد — مثلاً بعد از ثبت یک فرم بدون تغییر صفحه.

205
Reset Content

به مرورگر می‌گوید فیلدهای فرم فعلی را پاک کند.

206
Partial Content

یک درخواست بازه‌ای (Range) موفق بود — پایه‌ی استریم ویدیو و دانلود قابل‌ادامه.

§8

Status Codes — 3xx Redirection

300
Multiple Choices

آدرس به چند نسخه از یک منبع اشاره می‌کند (مثلاً چند زبان)؛ سرور فهرستی از گزینه‌ها برمی‌گرداند.

301
Moved Permanently

منبع برای همیشه جابه‌جا شده؛ آدرس جدید در هدر Location است.

302
Found

جابه‌جایی موقت — درخواست‌های بعدی همچنان باید از آدرس قدیمی استفاده کنند.

304
Not Modified

نسخه‌ی محلی کلاینت هنوز معتبر است؛ سرور محتوایی نمی‌فرستد.

302 vs 303 vs 307

در HTTP/1.0، مرورگرها بعد از دریافت 302 روی یک درخواست POST، ریدایرکت را با GET دنبال می‌کردند — یعنی نوع درخواست عوض می‌شد. HTTP/1.1 برای رفع این ابهام، کد 303 را برای همین رفتار صریح اضافه کرد، و 307 را برای ریدایرکت موقت بدون تغییر نوع درخواست. نتیجه: سرور باید نسخه‌ی HTTP کلاینت را بداند تا کد درست را انتخاب کند.

§9

Status Codes — 4xx Client Error

400
Bad Request

درخواست کلاینت بدفرم بوده — سرور اصلاً نتونسته درکش کنه.

401
Unauthorized

باید قبل از دسترسی به این منبع، احراز هویت کنی.

402
Payment Required

فعلاً استفاده نمی‌شود؛ برای آینده کنار گذاشته شده.

403
Forbidden

سرور درخواست را رد کرده. معمولاً دلیل رد را نمی‌گوید تا اطلاعات اضافه لو نرود.

404
Not Found

همون خطای معروف. سرور آدرس درخواستی را نمی‌شناسد.

405
Method Not Allowed

متد استفاده‌شده برای این آدرس مجاز نیست؛ هدر Allow متدهای مجاز را نشان می‌دهد.

406
Not Acceptable

هیچ نسخه‌ای از منبع، با ترجیحات Accept کلاینت مطابقت ندارد.

407
Proxy Authentication Required

مثل 401، ولی برای پروکسی‌ای که نیاز به احراز هویت دارد.

408
Request Timeout

کلاینت خیلی طول داده تا درخواستش را کامل کند؛ سرور اتصال را بسته است.

409
Conflict

این درخواست با وضعیت فعلی منبع تداخل دارد.

410
Gone

شبیه 404، با این فرق که سرور می‌داند این منبع قبلاً بوده و عمداً حذف شده — معمولاً هنگام نگهداری سایت استفاده می‌شود.

411
Length Required

سرور نیاز دارد درخواست حتماً هدر Content-Length داشته باشد.

412
Precondition Failed

یکی از شرط‌های درخواست شرطی برقرار نبوده.

413
Request Entity Too Large

بدنه‌ی درخواست بزرگ‌تر از چیزی است که سرور می‌تواند پردازش کند.

414
Request URI Too Long

آدرس درخواستی طولانی‌تر از حدی است که سرور قبول می‌کند.

415
Unsupported Media Type

سرور نوع محتوای فرستاده‌شده را نمی‌فهمد یا پشتیبانی نمی‌کند.

416
Requested Range Not Satisfiable

بازه‌ای که برای منبع درخواست شده، نامعتبر بوده یا قابل تأمین نیست.

417
Expectation Failed

سرور نتوانسته انتظاری که در هدر Expect آمده بود را برآورده کند.

§10

Status Codes — 5xx Server Error

500
Internal Server Error

خود سرور به یک خطا خورده و نتوانسته درخواست را سرویس بدهد.

501
Not Implemented

درخواست فراتر از توانایی سرور است — مثلاً متدی که سرور اصلاً پشتیبانی نمی‌کند.

502
Bad Gateway

سرور به‌عنوان پروکسی یا gateway، پاسخ نامعتبری از حلقه‌ی بعدی زنجیره گرفته است.

503
Service Unavailable

سرور فعلاً نمی‌تواند سرویس بدهد، ولی بعداً می‌تواند؛ هدر Retry-After می‌تواند زمان تقریبی را بگوید.

504
Gateway Timeout

مثل 408، ولی این‌بار یک gateway یا پروکسی منتظر پاسخ سرور دیگری مانده و تایم‌اوت شده.

505
HTTP Version Not Supported

سرور نسخه‌ای از پروتکل که در درخواست آمده را نمی‌تواند یا نمی‌خواهد پشتیبانی کند.

Proxies & 5xx

پروکسی‌ها وقتی در برقراری ارتباط با سرور دیگری به مشکل می‌خورند، معمولاً همین کدهای 5xx را برای توصیف مشکل صادر می‌کنند.

§11

HTTP Headers

General Headers

هدرهای عمومی که هم تو درخواست هم تو پاسخ استفاده می‌شوند، چون معنیشان فرقی نمی‌کند کی فرستاده باشدشان.

Date, Connection, Via, Cache-Control, Upgrade, Trailer
Request Headers

فقط در درخواست‌ها معنی دارند — اطلاعاتی درباره‌ی اینکه کلاینت کیست و چه چیزی می‌خواهد.

Accept, Accept-Language, Accept-Encoding, User-Agent, Referer, Host, Cookie

هدرهای Accept دوطرفه سودمندند: کلاینت دقیقاً همان چیزی که می‌خواهد می‌گیرد، سرور هم پهنای باند را برای چیزی که کلاینت نمی‌تواند استفاده کند هدر نمی‌دهد.

Conditional Request Headers

برای گذاشتن یک شرط روی درخواست — مثلاً «فقط اگر از این تاریخ به بعد تغییر کرده، برایم بفرست».

If-Modified-Since, If-None-Match, If-Match, If-Range, Range
Response Headers

اطلاعاتی درباره‌ی سرور یا نحوه‌ی رفتار با پاسخ به کلاینت می‌دهند.

Server, Retry-After, Age, Warning, Accept-Ranges, Vary
Security Headers

مکانیزم چالش/پاسخ برای احراز هویت، به‌علاوه‌ی کوکی‌ها.

Authorization, WWW-Authenticate, Cookie, Set-Cookie, Proxy-Authenticate
Entity Headers

درباره‌ی خود بدنه‌ی پیام (body) صحبت می‌کنند؛ می‌توانند هم در درخواست باشند هم در پاسخ.

Content-Type, Content-Length, Content-Encoding, Content-Language, Content-Range, Content-MD5

Allow لیست متدهای مجاز روی یک منبع را می‌دهد. Location آدرس واقعی یا جدید منبع را نشان می‌دهد — همان چیزی که در ریدایرکت‌های 301/302 دیدیم.

ETag

یک شناسه‌ی یکتا برای نسخه‌ی فعلی یک منبع. کلاینت بعداً با هدر If-None-Match می‌پرسد «نسخه‌ای که دارم هنوز با این ETag یکی است؟» — دقیق‌تر از If-Modified-Since، چون واقعاً محتوا را چک می‌کند، نه فقط تاریخ را.

Extension Headers

هدرهای غیراستاندارد که برنامه‌نویس‌ها خودشان ساخته‌اند ولی هنوز در مشخصات رسمی HTTP نیستند. برنامه‌های HTTP باید بتوانند این هدرها را تحمل کنند و منتقل کنند، حتی اگر معنیشان را نفهمند.

§12

Connection Desync & Request Smuggling

Idempotency

یعنی هر بار اجرا کنی، نتیجه یکیه. GET، PUT، DELETE ایدمپوتنت‌اند؛ POST نیست — برای همینه که مرورگر با ریلود کردن یه صفحه‌ی پرداخت، ازت می‌پرسه «دوباره ارسال بشه؟»

Pipelining

چند درخواست را بدون منتظر ماندن برای جواب هرکدام، پشت‌سرهم روی یک اتصال می‌فرستی. سریع‌تره، ولی چون پاسخ‌ها هیچ شماره‌ترتیبی ندارند، اگر ترتیب به‌هم بخورد، سرویس‌گیرنده گیج می‌شود — دقیقاً همین بی‌نظمی، زمینه‌ساز حملات بعدی است.

HTTP Request Smuggling

وقتی دو سرور روی یک زنجیره (مثلاً یک پروکسی جلویی و یک سرور اصلی)، سر «این درخواست کجا تمام می‌شود» با هم اختلاف دارند. مهاجم یک تکه داده را در این اختلاف قایم می‌کند تا داخل درخواست بعدیِ یک کاربر دیگر بچسبد — مثل قایم‌کردن یک نامه‌ی دوم داخل پاکتی که رویش نوشته «فقط یک نامه».

Desync Attacks

نام کلی‌تری برای همین خانواده حمله — یعنی «ناهم‌زمانی» بین دو سرور در تشخیص مرز پیام‌ها. Request Smuggling رایج‌ترین و شناخته‌شده‌ترین نوع Desync است.

CL.TE

فرانت‌اند به هدر Content-Length اهمیت می‌دهد، بک‌اند به Transfer-Encoding. فرانت‌اند زودتر از موعد فکر می‌کند پیام تمام شده، در حالی که بک‌اند هنوز منتظر رسیدن قطعه‌ی صفر است.

TE.CL

دقیقاً برعکس — فرانت‌اند به Transfer-Encoding اهمیت می‌دهد، بک‌اند به Content-Length. اینجا فرانت‌اند دیرتر تشخیص می‌دهد پیام تمام شده، در حالی که بک‌اند زودتر بریده و منتظر داده‌ی بعدی می‌ماند.

Why It Matters for Bug Bounty

چون سازمان‌های بزرگ معمولاً چند لایه پروکسی/CDN با پیاده‌سازی‌های متفاوت HTTP دارند، همین اختلاف کوچک تفسیر، دریچه‌ی سرقت داده‌ی کاربران دیگر، دور زدن احراز هویت، یا مسموم‌کردن کش را باز می‌کند. تمرین عملی: PortSwigger Web Security Academy، بخش Request Smuggling.
