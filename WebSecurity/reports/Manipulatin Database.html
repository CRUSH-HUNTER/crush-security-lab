تلاش‌ها، خطاها، و راه‌حل‌ها

Attempts, Errors & Fixes — Full Timeline
ERROR #1

UPDATE مستقیم در sqlitebrowser — Read-only database

اولین تلاش: اجرای مستقیم UPDATE در sqlitebrowser روی فایل کپی‌شده:

-- Command attempted:
UPDATE Wallets SET balance = 0 WHERE UserId = 2;

-- Error received:
Execution finished with errors.
Result: attempt to write a readonly database
At line 1:
UPDATE Wallets SET balance = 0 WHERE UserId = 2;

دلیل خطا: فایل juiceshop.sqlite با docker cp کپی شد و ownership اش به root:root تعلق داشت. فقط root می‌تونست بنویسه.

DIAGNOSIS

بررسی permission های فایل

$ ls -la ~/juiceshop.sqlite

-rw-r--r-- 1 root root 258048 Aug 30 17:50 /home/mary/juiceshop.sqlite
#           ^    ^
#           |    └── group: root (read only)
#           └── owner: root (read/write, but we're not root)
# mary user has only READ permission (r--)
FIX #1 — SOLVED ✓

تغییر ownership فایل به mary

$ sudo chown mary:mary ~/juiceshop.sqlite
$ chmod 644 ~/juiceshop.sqlite

$ ls -la ~/juiceshop.sqlite
-rw-r--r-- 1 mary mary 258048 Aug 30 17:50 /home/mary/juiceshop.sqlite
#                 ^^^^
#                 now owned by mary → write access granted

بعد از close و reopen کردن sqlitebrowser، دستور UPDATE بدون خطا اجرا شد.

ERROR #2

تغییر توی فایل محلی — سایت تغییر نکرد

بعد از UPDATE موفق در sqlitebrowser، توی سایت Juice Shop موجودی تغییری نداشت.

// Problem:
~/juiceshop.sqlite        ← local copy (what we edited)
/juice-shop/data/juiceshop.sqlite  ← live database inside Docker (unchanged!)

// These are TWO different files
// Editing the local copy doesn't affect the running application

دلیل: Juice Shop داده‌ها رو از دیتابیس داخل کانتینر می‌خونه — نه از نسخه‌ی محلی.

FIX #2 — SOLVED ✓

اجرای مجدد Juice Shop + دستکاری مستقیم داخل کانتینر

-- Step 1: Run Juice Shop again
$ sudo docker run -d -p 127.0.0.1:3000:3000 bkimminich/juice-shop

-- Step 2: Get new container ID
$ sudo docker ps
CONTAINER ID   IMAGE                   STATUS
f5f3ae3f9615   bkimminich/juice-shop   Up 2 minutes

-- Step 3: Manipulate database DIRECTLY inside container
$ sudo docker exec -it f5f3ae3f9615 /nodejs/bin/node -e \
"const {Sequelize}=require('/juice-shop/node_modules/sequelize');
const db=new Sequelize({dialect:'sqlite',storage:'/juice-shop/data/juiceshop.sqlite'});
db.query('UPDATE Wallets SET balance=0 WHERE UserId=2').then(()=>{
  console.log('Jim wallet: 0');
  db.query('UPDATE Wallets SET balance=balance+100 WHERE UserId=1').then(()=>{
    console.log('Admin wallet: +100');
    process.exit(0);
  });
});"

-- Output:
Executing (default): UPDATE Wallets SET balance=0 WHERE UserId=2
Jim wallet: 0
Executing (default): UPDATE Wallets SET balance=balance+100 WHERE UserId=1
Admin wallet: +100    ← SUCCESS!

درس‌های فنی از این مسیر

Technical Lessons Learned
خطاRoot CauseFix
Read-only database docker cp → root:root ownership sudo chown mary:mary
تغییر در سایت اعمال نشد فایل محلی ≠ دیتابیس زنده‌ی Docker دستکاری مستقیم داخل کانتینر
Container not running آیدی اشتباه (hello-world به‌جای juice-shop) docker run مجدد + آیدی جدید

تفاوت دو روش دستکاری

Method 1 — Edit local copy then docker cp back:
  + Easier to use GUI tools (sqlitebrowser)
  - Two-step process (edit + copy back)
  - Risk of container restart wiping changes
  - File ownership issues

Method 2 — Execute directly inside container (BETTER):
  + Changes apply immediately to live database
  + No file transfer needed
  + No ownership issues
  - Requires Node.js/Sequelize knowledge
  - No GUI — command line only

راه‌حل‌های پیشنهادی

// Fix 1 — Database encryption:
SQLCipher or similar → even with file access, data is unreadable

// Fix 2 — Principle of least privilege:
App DB user: SELECT, INSERT, UPDATE only (no DROP, no direct file access)
Separate read-only user for reporting

// Fix 3 — File system permissions:
chmod 600 /app/data/production.db
chown app_user:app_group /app/data/production.db
// Only the application process can read/write

// Fix 4 — Database audit logging:
Log ALL write operations with timestamp + source IP
Alert on unusual UPDATE patterns (large balance changes)

// Fix 5 — Defense in depth:
Prevent SQLi → prevent RCE → prevent shell access
Each layer reduces risk of reaching the database directly
