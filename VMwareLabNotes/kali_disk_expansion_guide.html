// KALI VM · DISK EXPANSION LOG

راهنمای افزایش فضای دیسک Kali Linux

مستندسازی کامل فرایند تشخیص و رفع کمبود فضای دیسک روی VMware Workstation — از عیب‌یابی اولیه تا گسترش نهایی پارتیشن با GParted Live.

قبل: sda 20G بعد: sda 50G ابزار: GParted Live هایپروایزر: VMware Workstation
1

تشخیص مشکل

Diagnosis
1

بررسی وضعیت اولیه دیسک و RAM

با lsblk -f و df -h مشخص شد که sda1 (روت سیستم) از ۱۹ گیگ ظرفیت، ۱۵ گیگ پر شده بود؛ درحالی‌که یک دیسک دوم (sdb) به‌تازگی اضافه شده بود اما به‌عنوان دیسک کاملاً جدا شناسایی می‌شد، نه بخشی از sda.

lsblk -f
df -h
نکته: وقتی یک دیسک جدید به ماشین مجازی اضافه می‌شود، هایپروایزر آن را همیشه به‌صورت یک دیسک مستقل (مثلاً /dev/sdb) می‌شناسد، نه اینکه خودکار به پارتیشن اصلی بچسباند.
2

پیدا کردن بزرگ‌ترین مصرف‌کننده‌ی فضا

با نصب و اجرای ncdu و دستورات du -sh روی مسیرهای مشکوک، مشخص شد اصلی‌ترین مصرف‌کننده‌ی فضا، پوشه‌ی /usr (حدود ۱۳ گیگ) بود — شامل ابزارهای امنیتی نصب‌شده روی Kali مثل Burp Suite، exploitdb، john، peass و کتابخانه‌های سیستمی (python3، llvm، gcc).

sudo apt install ncdu -y
sudo ncdu /
sudo du -sh /usr /var/log /opt
sudo du -h --max-depth=1 /usr/lib | sort -rh | head -15
نتیجه‌گیری: این حجم واقعی و در حال استفاده بود، نه فایل زباله. تصمیم نهایی: به‌جای پاک‌سازی، ظرفیت خود دیسک sda باید افزایش می‌یافت.
2

مهاجرت داده‌ی Docker به دیسک دوم

Migrating Docker to sdb
1

آماده‌سازی و مانت کردن دیسک دوم

دیسک خام sdb پارتیشن‌بندی، فرمت و روی مسیر /mnt/data مانت شد.

sudo fdisk /dev/sdb        # n → p → Enter → Enter → w
sudo partprobe /dev/sdb
sudo mkfs.ext4 /dev/sdb1
sudo mkdir -p /mnt/data
sudo mount /dev/sdb1 /mnt/data
2

ماندگار کردن مانت با fstab

sudo blkid /dev/sdb1
sudo nano /etc/fstab
# افزودن خط:
# UUID=xxxx-xxxx  /mnt/data  ext4  defaults  0  2
3

انتقال داده‌ی Docker

سرویس Docker متوقف شد، داده‌ها با rsync به مسیر جدید کپی شدند، و در daemon.json مسیر ذخیره‌سازی جدید معرفی شد.

sudo systemctl stop docker
sudo systemctl stop docker.socket
sudo mkdir -p /mnt/data/docker
sudo rsync -aP /var/lib/docker/ /mnt/data/docker/

sudo nano /etc/docker/daemon.json
# { "data-root": "/mnt/data/docker" }

sudo systemctl start docker
docker info | grep "Docker Root Dir"
sudo rm -rf /var/lib/docker
نتیجه: فضای اشغال‌شده توسط Docker از sda جدا شد، اما بررسی‌های بعدی نشان داد مشکل اصلی جای دیگری (پوشه‌ی /usr) بود، نه Docker.
3

افزایش ظرفیت دیسک از VMware

Expanding the Virtual Disk
1

خاموش کردن کامل ماشین مجازی

گسترش دیسک فقط وقتی ممکن است که VM کاملاً خاموش باشد (نه Suspend).

sudo poweroff
2

حذف اسنپ‌شات‌های موجود

دکمه‌ی Expand در VMware تا وقتی اسنپ‌شات وجود داشته باشد غیرفعال می‌ماند.

VM → Snapshot → Snapshot Manager → Delete All
3

گسترش دیسک از تنظیمات VM

VM → Settings → Hard Disk (SCSI) → Expand...
# اندازه‌ی جدید وارد شد: از 20GB به 50GB
هشدار: این مرحله فقط فضای خام دیسک را در سطح هایپروایزر افزایش می‌دهد. پارتیشن و فایل‌سیستم داخل Kali هنوز از این فضای اضافه خبر ندارند — مرحله‌ی بعدی برای همین لازم است.
4

بوت از GParted Live

Booting GParted Live ISO
1

چرا از GParted Live استفاده کردیم؟

پارتیشن روت (sda1) در حالت عادی مانت و در حال اجراست، پس نمی‌توان آن را از داخل خود سیستم به‌صورت امن گسترش داد. GParted Live یک سیستم‌عامل کوچک است که از روی ISO بوت می‌شود و پارتیشن‌بندی را از بیرون سیستم اصلی انجام می‌دهد.

2

وصل کردن فایل ISO

VM → Settings → CD/DVD (IDE)
→ Use ISO image file → مسیر فایل gparted-live.iso
→ تیک Connect at power on
3

ورود به فریمور برای تغییر ترتیب بوت

چون فشردن Esc در لحظه‌ی روشن‌شدن همیشه قابل‌اعتماد نیست، از مسیر مطمئن‌تر زیر استفاده شد:

VM → Power → Power On to Firmware

در محیط PhoenixBIOS، از تب Boot، گزینه‌ی CD-ROM Drive با کلید + بالای Hard Drive آورده شد، سپس F10 برای ذخیره و خروج زده شد.

نتیجه: سیستم با موفقیت وارد محیط گرافیکی GParted شد و /dev/sda (50 گیگ) با پارتیشن‌های sda1 (18.92G)، sda2/sda5 (extended/swap، 1.08G) و 30G فضای unallocated نمایش داده شد.
5

بازآرایی پارتیشن‌ها در GParted

Repartitioning
1

حذف پارتیشن Swap و Extended

چون پارتیشن روت قبل از پارتیشن extended/swap قرار داشت، نمی‌شد مستقیم آن را گسترش داد. اول باید موانع کنار زده می‌شدند.

راست‌کلیک روی /dev/sda5 (linux-swap) → Delete
راست‌کلیک روی /dev/sda2 (extended) → Delete
نتیجه: کل فضای بعد از sda1 (حدود 31 گیگ) به‌صورت یکپارچه unallocated شد.
2

گسترش پارتیشن روت (sda1)

با ۲ گیگ فاصله برای ساخت swap جدید در انتها.

راست‌کلیک روی /dev/sda1 → Resize/Move
→ New size: تا 48.00 GiB (2 GiB برای swap باقی گذاشته شد)
نکته: این مرحله برخلاف حذف پارتیشن، واقعاً فایل‌سیستم ext4 را گسترش می‌دهد و چند دقیقه طول می‌کشد.
3

ساخت پارتیشن Swap جدید

راست‌کلیک روی فضای unallocated باقی‌مانده → New
→ File system: linux-swap
→ Add
4

اعمال نهایی تغییرات

بعد از تایید صف عملیات (حذف swap قدیمی، گسترش sda1 به 48G، ساخت swap جدید 2G)، دکمه‌ی تیک سبز Apply زده شد.

دکمه‌ی Apply (تیک سبز) در نوار ابزار GParted
6

بازگشت به Kali و نهایی‌سازی

Post-Reboot Cleanup
1

خروج از GParted و قطع اتصال ISO

قبل از ری‌استارت، اتصال ISO باید قطع شود تا سیستم دوباره وارد GParted نشود و به‌جایش بوت عادی Kali انجام شود.

GParted → Quit → Reboot
VM → Settings → CD/DVD (IDE) → برداشتن تیک Connect at power on
2

پیدا کردن UUID پارتیشن Swap جدید

چون یک پارتیشن swap کاملاً جدید ساخته شده، UUID آن با چیزی که در fstab قدیمی ثبت بود فرق دارد.

lsblk -f
sudo blkid | grep swap
3

به‌روزرسانی /etc/fstab

sudo nano /etc/fstab
# جایگزینی UUID قدیمی خط swap با UUID جدید
4

فعال‌سازی و تایید نهایی

sudo swapon -a
free -h
معیار موفقیت: اگر مقدار Swap در خروجی free -h غیر صفر باشد، یعنی سیستم با فضای گسترش‌یافته‌ی جدید (sda1 = 48G، swap = 2G) کاملاً سالم و آماده به کار است.
